# 0. 먼저 30분만 — 개념과 용어 (완전 초보자용)

## 0-1. 모델을 "만드는" 3가지 방식
| 방식 | 비유 | 설명 |
|---|---|---|
| **scratch (맨땅 학습)** | 아기를 처음부터 가르치기 | 아무것도 모르는 빈 모델에 우리 데이터만으로 전부 가르침. 느리고 데이터 많이 필요. |
| **전이학습 (Transfer Learning)** | 이미 사물을 아는 사람에게 "안전모"만 새로 가르치기 | 남이 **대량 데이터(COCO, 80종 사물)**로 미리 학습시킨 모델(`yolov8s.pt`)을 **출발점**으로 가져와, 우리 문제로 이어 학습. 훨씬 빠르고 잘 됨. |
| **파인튜닝 (Fine-tuning)** | 잘하는 사람을 "살짝만" 더 다듬기 | 이미 어느 정도 학습된 우리 모델을 **아주 낮은 학습률**로 조금 더 손봄. 기존 실력을 깨지 않으면서 개선. |

> 우리 프로젝트는 **전이학습으로 시작 → 파인튜닝을 여러 번 쌓아** 최종 모델을 만들었습니다. (round8에서 scratch와 비교해 "전이학습이 낫다"를 직접 증명)

## 0-2. 성능을 "재는" 법
- **mAP50**: 탐지 종합 점수(0~1). 박스를 얼마나 잘·정확히 치는지. **높을수록 좋음.**
- **val(검증) vs test(시험)**:
  - **val** = 학습하면서 들여다보는 셋. 튜닝 기준. (학생이 푸는 모의고사)
  - **test** = 학습에 **한 번도 안 쓴** 셋. 진짜 실력. (실제 수능)
  - **val만 높고 test가 낮으면 = 과적합(overfitting)** = "모의고사만 외운 학생". → 이게 우리 round5에서 실제로 벌어졌고, 그걸 보고 다음 수를 뒀습니다.
- **클래스별 mAP**: 전체 점수만 보면 어떤 클래스가 망가졌는지 모름 → fallen/no_helmet/ok **각각** 봐야 함. (round3에서 이게 결정적이었음)

## 0-3. 데이터를 "다루는" 법
- **클래스 불균형**: 클래스별 데이터 수 차이. ok(안전모)는 흔하고 **fallen(전도)은 드묾** → 모델이 흔한 쪽만 잘 맞추는 편향이 생김.
- **재라벨링 / 리매핑**: 공개 데이터마다 클래스 번호·이름이 제각각 → **우리 3클래스(0/1/2)로 번호를 다시 매기는 것.**
- **카타스트로픽 포게팅(catastrophic forgetting)**: 좁은 데이터로 파인튜닝하다 **기존에 알던 클래스를 잊어버리는 현상.** (round2에서 실제로 당함)

## 0-4. ★ 파라미터 사전 — 우리가 라운드마다 만진 값들이 "무엇을·왜"
| 파라미터 | 무엇인가 | 키우면 / 줄이면 |
|---|---|---|
| **lr0 (학습률)** | 한 번에 얼마나 크게 배우는가 | 크면 빨리 배우지만 거칠다(전이학습 시작 0.01). **작으면 기존 지식 보존하며 미세 조정**(파인튜닝 0.005→0.003→0.001). |
| **epochs** | 데이터를 몇 번 반복 학습 | 우리는 50→100. |
| **batch** | 한 번에 몇 장씩 보고 갱신 | 크면 안정적·메모리↑(16→32→40). |
| **warmup** | 초반 몇 에폭은 lr을 서서히 올림 | 파인튜닝일수록 짧게(3→1) — 이미 좋은 출발점이라 천천히 데울 필요 적음. |
| **patience** | val이 N에폭 안 좋아지면 자동 중단(조기종료) | 길면 더 기다림(20→35). |
| **cls** | 분류(클래스 맞히기) 손실 가중 | 우리는 2.0 고정. **⚠️ 이건 전체 단일값 — YOLOv8엔 "클래스별로 따로" 주는 옵션이 없음(round9·10 참고).** |
| **증강(augmentation)** | 학습 이미지를 일부러 변형해 다양화 → **과적합 방지·일반화↑** | 아래 ↓ |

**증강 세부 (round6부터 강하게 줌):**
| 증강 | 무엇을 하나 | 왜 도움 되나 |
|---|---|---|
| **degrees** | 이미지를 ±N도 **회전** (15→30→35) | 사람이 기울거나 누운 모습(특히 **fallen**)을 다양하게 학습 |
| **flipud** | **상하 반전**(0→0.3) | 쓰러진 사람 등 뒤집힌 패턴 학습 (fallen 강화용) |
| **fliplr** | 좌우 반전(0.5) | 좌우 대칭 다양성 |
| **scale** | 확대/축소(0.5→0.7) | 멀고 가까운 크기 다양화 |
| **mosaic** | 4장을 한 장으로 합쳐 학습 | 다양한 배경·맥락 |
| **mixup** | 두 이미지를 반투명 겹침(0→0.15) | 경계가 애매한 상황에 강인 |
| **copy_paste** | 객체를 오려 다른 이미지에 붙임(0→0.1) | 드문 객체 수를 늘려 불균형 완화 |

> 핵심 직관: **증강을 키우면 "똑같은 사진을 외우기" 어려워져서, 처음 보는 상황(test)에 강해진다.** ← round5→6의 결정적 수.

## 0-5. loss 지표 — "참고로" 본 것 (box_loss 등)
학습 중에는 mAP(결과 점수) 말고도 **loss(오차)** 가 기록됩니다. 주 지표는 아니지만, **학습이 건강하게 되고 있는지**를 보는 참고가 됐습니다.

**3가지 loss가 무엇을 뜻하나** (각각 train/val 두 버전):
| loss | 무엇을 재나 | 높으면 |
|---|---|---|
| **box_loss** | 박스를 **얼마나 정확한 위치·크기**로 치는가 | 위치가 부정확 |
| **cls_loss** | 박스 안 객체의 **클래스를 맞히는가** (fallen/no_helmet/ok) | 분류를 헷갈림 |
| **dfl_loss** | 박스 **경계를 얼마나 정밀하게** 잡는가 (distribution focal loss) | 경계가 뭉툭 |

**우리 실제 데이터로 본 2가지 교훈 (단순 해석 금지):**

**① "train loss < val loss = 과적합"을 그대로 믿으면 안 됨**
우리 cls_loss는 오히려 **train이 val보다 높습니다** (round7: train 2.72 / **val 2.13**, round5: 2.27 / 1.93).
- 보통은 val이 더 높아야 하는데 왜 반대일까? → **증강(회전·mixup 등)은 train 이미지에만 적용**되어 학습 이미지가 더 어렵기 때문. val은 원본이라 더 쉬움.
- 즉 **loss 숫자만 단독으로 보면 "과적합인가?"를 오판**할 수 있음 → 반드시 **mAP와 같이** 봐야 함. (이것도 "지표 하나만 믿지 마라"의 한 사례)

**② loss가 실제로 판단에 관여한 곳 = 조기종료(patience)**
- **round5**: val 쪽 지표가 **ep1 이후 더 나아지지 않아 21에폭에서 자동 중단**(설정은 100). val_box_loss가 ep1 1.075에서 더 안 내려감 → "그만 배워라" 신호. (그리고 실제로 test도 0.866으로 정체 — loss 정체와 일치)
- **round6**: val_box_loss가 1.90 → 1.11로 **끝까지 꾸준히 내려가 100에폭을 다 씀** = 건강한 수렴.
- → loss/val 지표의 **추세**가 "더 돌릴지 멈출지"를 가르는 **조기종료 트리거**로 작동.

**결론 — loss는 이렇게 쓴다:**
- **loss = "학습이 건강하게 수렴하나"를 보는 _과정_ 지표** (발산·정체하면 lr/데이터 의심, 조기종료 트리거).
- **mAP = "실제로 잘 맞히나"를 보는 _결과_ 지표** (최종 판단).
- 그래서 **mAP를 주로, loss를 보조로** 본 것이 올바른 사용법이었음. (loss를 결과 판단에 쓰면 위 ①처럼 오판 위험)

# 1. 데이터 수집 & 라벨링 — 누가, 어떻게, 몇 장

우리 데이터는 **여러 출처를 모아 하나의 3클래스 체계로 재매핑**한 것입니다.

**최종 클래스 (3개):**
- `0 = fallen` (쓰러진 사람)
- `1 = no_helmet` (안전모 미착용 — **맨얼굴(head)·캡모자·일반모자 전부 포함**)
- `2 = ok` (안전모 착용)

> **왜 캡/모자를 no_helmet에 합쳤나?** 처음엔 cap을 별도 클래스로 빼볼까 했지만, 그러면 모델이 **맨얼굴·모자를 ok(안전모)로 착각**하거나 no_helmet 탐지를 빼앗기는 문제가 생김. 안전 감시는 "미착용을 넓게 잡는 것"이 목적이라 **모자류·맨얼굴을 전부 no_helmet으로 통합**하는 게 맞았음.

## 1-1. 출처별 — 누가 어떻게 라벨링했나
| 출처 | 장수 | 누가/어떻게 | 원본 클래스 | → 우리 클래스 |
|---|---|---|---|---|
| **Roboflow 안전모셋** | 다수 | **이미 라벨링되어 있던 공개셋** (우리는 클래스 **이름만 변경**) | `[head, helmet]` | head→**no_helmet(1)**, helmet→**ok(2)** |
| **data_hat** | **221장** (176+45) | **우리 팀원 전원이 AML Studio에서 함께** 손라벨링 (캡모자·모자 쓴 사람) | `no_helmet` | →**no_helmet(1)** |
| **cap_labeled** | **192장** | **내가 Label Studio로 직접** — 모자만이 아니라 **모자 쓴 "얼굴"까지 박스**로 라벨링 | `no_helmet/ok/person` | no_helmet→1, ok→2, person 제외 |
| **Kaggle hardhat (VOC)** | 다수 | 공개셋 (XML→YOLO 변환) | `head/helmet/person` | head→1, helmet→2, person 제외 |
| **fallen ×3 (캐글+Roboflow)** | 다수 | 공개셋 — `fallen_roboflow`, `fallen(laying, 자세→박스 변환)`, `fallen2` | Fall/laying/fall | →**fallen(0)** |

> 통합 스크립트: `src/05_remap_merge_all.py` (전 출처를 0/1/2로 리매핑 후 병합).

## 1-2. 통합 재매핑 한눈에
```
[ no_helmet(1)로 ] ← roboflow:head + 팀원 data_hat + 내 cap_labeled(모자얼굴) + hardhat:head
[ ok(2)로       ] ← roboflow:helmet + cap_labeled:ok + hardhat:helmet
[ fallen(0)로   ] ← fallen_roboflow + fallen(laying) + fallen2   (person 라벨은 전부 제외)
```

## 1-3. 라벨링에서 어려웠던 점 (팀원 공유)
1. **출처마다 클래스 번호가 다 달라서** 전부 우리 0/1/2로 다시 매핑해야 했음.
2. **캡모자 처리** — 별도 클래스 vs no_helmet 병합을 고민하다 **병합**으로 결정(위 이유).
3. **fallen 라벨이 부실** — 어떤 건 "자세(pose) 좌표"라 **박스(bbox)로 변환**해야 했고, 이 변환/품질 문제가 **round3 실패의 원인**이 됨(아래).

# 2. 라운드별 상세 (round1 → round10)

> 각 라운드: **📦데이터 / 🏷️라벨·클래스 / ⚙️설정과 "왜 이 값으로" / 🔴문제 / 🟢어떤 지표 보고 다음 결정 / 📊결과**
> **round1~3은 사실상 "연습"** 단계였습니다. 진짜 본 게임은 round4부터.

---
## 🟦 [연습] Round 1 — "전이학습으로 안전모가 풀리나?" 확인
- **📦 데이터**: `data_remapped` (2클래스), train **4,916장** — no_helmet 911장/4,612박스, ok 4,503장/13,919박스. *(시작부터 ok가 3배 많음 = 불균형의 씨앗)*
- **🏷️ 라벨·클래스**: Roboflow의 `[head, helmet]`을 **이름만** head→no_helmet, helmet→ok로 변경. fallen 아직 없음.
- **⚙️ 설정과 왜**: base=`yolov8s.pt`(**전이학습** 출발점), **lr0 0.01**(새 분류 헤드를 처음 배우니 표준 학습률), ep 50, batch 16, 증강 약(degrees 0/mixup 0).
  - *왜 이렇게?* "일단 되는지부터 본다"라서 기본값 위주로 가볍게.
- **🔴 문제**: 없음 — 검증 단계.
- **🟢 판단 → 다음**: val/test **0.972/0.957**로 잘 나옴 → "접근법 OK". 다만 **캡/모자 같은 경계 케이스가 약할 것 같다**는 직관 → round2에서 모자 데이터로 보강하기로.
- **📊 결과**: **val 0.972 / test 0.957** (no_helmet 0.953 · ok 0.961). → 여기서 결과를 자꾸 까먹어서 **MLflow 기록 시작**.

---
## 🟦 [연습] Round 2 — 모자 보강 파인튜닝 → ⚠️ **포게팅 사고**
- **📦 데이터**: `data_hat` (**팀원 공동 라벨링, 221장**) — 사실상 **no_helmet 한 클래스**(176장/223박스)뿐. ok 데이터가 거의 없음(이게 사고의 씨앗).
- **🏷️ 라벨·클래스**: 모자/모자쓴사람을 no_helmet으로.
- **⚙️ 설정과 왜**: base=**round1 best**(이어서 학습=파인튜닝), **lr0 0.001**(round1의 0.01에서 **10배 낮춤** — 기존 지식을 깨지 않으려고. 이게 파인튜닝의 정석), cls 2.0(분류 가중↑).
- **🔴 문제 (중요한 교훈)**: hat-val(no_helmet만 든 45장)에선 **mAP 0.99·precision 1.0**으로 "완벽"해 보였음. 그런데 **전체 2클래스로 다시 재보니 0.165로 폭락** — **ok 정확도 0.000**(완전히 잊음!).
  - 원인① **카타스트로픽 포게팅**: no_helmet만 든 좁은 데이터로 파인튜닝 → ok 지식 소실.
  - 원인② **단일클래스 val 착시**: 평가셋에 no_helmet뿐이라, 모델이 "전부 no_helmet"으로 찍어도 precision 1.0이 나옴(맞힐 게 그것뿐이라).
- **🟢 판단 → 다음**: 이 사고로 **2가지를 배움** → ① 좁은 단일클래스 파인튜닝은 위험 → **scratch로 깨끗이 다시 시작**(round3) ② **평가는 항상 전체 클래스로** 해야 한다. + 안전 요구상 **fallen 클래스 추가** 필요 → 3클래스로 확장.
- **📊 결과**: **val 0.165 / test 0.128** (ok 0.000). → "좋아 보이는 숫자에 속지 마라"의 산 증거.

## 🟦 [연습] Round 3 — 3클래스 첫 도전 → ❌ **실패 (fallen 완전 붕괴)**

## 🧪 Round 9·10 — fallen 불균형 대응 시도 → 미세 퇴보
- **❓ 의도 (내 생각)**: fallen 데이터가 상대적으로 적어 불균형하니, **"fallen에 가중치를 더 줘서" 끌어올리자**.
- **⚠️ 실제로 일어난 일 (데이터가 말해주는 것)**:
  - **YOLOv8 표준 학습엔 "클래스별로 loss 가중치를 따로 주는" 옵션이 없습니다.** (`cls`는 전체 단일값 2.0으로 round3~10 내내 동일)

  - 그리고 이걸 **Airflow DAG가 "직전 라운드 fallen mAP를 보고 자동으로" 더 세게 조정**(동적 파라미터).

- **📊 결과**: r9 **val 0.961/test 0.939**, r10 **val 0.956/test 0.935**. → round7 유지 확정.

# 5. 우리가 쓴 도구 — 무슨 기능이고 왜 썼나

## 🧪 MLflow — "실험 관리·비교" 도구
- **무엇**: 라운드마다 **파라미터(lr·증강·base 등)·지표(val/test/클래스별 mAP)·모델 파일**을 자동으로 기록·저장하는 도구.
- **왜 썼나 / 무엇이 좋았나**:
  - 10번 넘는 실험을 **한 화면에서 객관적으로 비교** → "어떤 설정이 나았나"를 기억이 아니라 **기록**으로 판단.
  - **이번 프로젝트의 결정적 순간들을 전부 MLflow로 잡아냄**: round2의 착시, round3의 fallen 0.000, round5의 val-test 격차, round9·10의 퇴보 추세.
  - = **"어디서 망가졌고, 무엇이 최선인지"를 보이게 해주는 눈.**

## ⏱️ Airflow — "워크플로 스케줄링·자동화" 도구
- **무엇**: 여러 작업(데이터확인→학습→검증→백업)을 **순서·의존성대로 자동 실행**하고 **스케줄/트리거**로 돌리는 도구(DAG = 작업 흐름도).
- **왜 썼나 / 무엇이 좋았나**:
  - **자면서 돌리고 싶어서** — 미리 DAG로 정의해두고 **스케줄 트리거**로 밤에 자동 실행.
  - **이전 라운드 결과(fallen mAP)를 보고 다음 라운드 파라미터를 자동으로 조정**(동적 파라미터) — round9·10이 그 예.
  - 단계 실패 시 재시도, 단계 의존성 관리 → 손으로 연결하다 생기는 실수 제거.
- **MLflow와 연동**: Airflow가 학습을 돌리는 동안, **에폭마다 지표를 MLflow로 자동 기록** → 자동 실행 + 자동 기록이 한 번에.

> 한 줄: **MLflow = "기록하고 비교하는 눈", Airflow = "알아서 돌리고 이어주는 손".**

# 6. MLOps 자동화 — 어디까지 했고, 무엇이 남았나
- **지금까지 달성 (ML 파이프라인 자동화)**:
  `데이터 확인 → 학습 → 검증(클래스별 mAP) → 이전 결과 기반 다음 라운드` 까지 **트리거 한 번으로 자동.**
- **아직 못 한 것**: **모델 레지스트리**(최고 모델을 버전·스테이지로 관리) + **원격 백업(Azure Blob)**.
- **다음에 이것까지 하면 = 완전한 MLOps 자동화**: 좋은 모델이 나오면 **자동으로 버전 등록 → 백업 → 배포 후보로 승격**까지 사람 손 없이.
  - (이전에 계획해 둔 round7 재현 DAG + Blob 업로드 + Registry 등록이 이 단계)

# 7. ⚖️ 사람이 판단해야 하는 지점 (자동화 안 되는 곳)
자동화(Airflow)는 "**실행·기록·검증·동적 미세조정**"을 하지만, **방향을 정하는 판단은 사람**이 했습니다.

| 과정 위치 | 사람의 판단 | 자동화의 역할 |
|---|---|---|
| 데이터 설계 | **클래스 정의**(캡→no_helmet 병합 결정) | — |
| 라벨링 | **라벨 품질 점검·재라벨링**(fallen bbox 수정) | — |
| 데이터 준비 | **균형 전략**(ok 언더샘플링 결정) | 샘플링 실행 |
| 라운드 설계 | **문제 진단→가설→파라미터 방향**(예: 과적합→증강↑) | 그 파라미터로 학습 실행 |
| 학습 중 | — | 에폭별 지표 MLflow 기록, 단계 재시도 |
| 라운드 후 | **결과 해석**(클래스별로 어디가 문제인지) | 검증·백업 자동 |
| 종료 | **"멈출 때" 판단**(r9/10 퇴보 보고 round7 확정) | 지표를 보여줌 |
| 배포 | **Production 채택 결정** | (향후) 레지스트리 승격 |

> 핵심: **자동화는 "잘 돌리고 잘 보여주는" 것, 판단은 그 지표를 보고 사람이.** 둘의 협업이 이 프로젝트의 방식이었습니다.

# 8. 팀원 예상 Q&A
- **Q. round3·4는 설정이 같은데 왜 결과가 다르죠?**
  A. 하이퍼파라미터는 일부러 똑같이 뒀어요. 차이는 **fallen 라벨을 제대로 된 박스로 재라벨링**한 것뿐. fallen test가 0.000→0.768로 살아난 게 증거 — **모델이 아니라 데이터 문제**였다는 걸 증명한 셈.
- **Q. round2가 0.165? 망한 거 아닌가요?**
  A. 망한 거 맞고, 그게 **값진 교훈**이에요. 좁은(모자만) 데이터로 파인튜닝하면 기존 클래스(ok)를 잊는다(**포게팅**)는 걸 직접 겪었고, 그래서 round3부터 평가·데이터 전략을 바꿨습니다.
- **Q. 왜 캡모자를 따로 클래스로 안 뺐나요?**
  A. 따로 빼면 맨얼굴/모자를 ok(안전모)로 오인하는 문제가 생겨서, **no_helmet으로 병합**하는 게 안전 감시 목적에 맞았어요.
- **Q. round9·10에서 fallen에 "가중치"를 준 거 아닌가요?**
  A. 그러려 했지만 **YOLOv8엔 클래스별 가중치 옵션이 없어서**, 대신 **fallen에 유리한 증강(회전·상하반전)을 강화**하는 방식으로 시도했어요. 결과는 오히려 미세 퇴보라 round7에서 멈췄습니다.
- **Q. round6이 test 0.965로 round7(0.957)보다 오히려 높은데 왜 round7이 최종?** (정직하게)
  A. **둘은 사실상 동급입니다.** 0.8%p 차이는 **런마다 생기는 노이즈 수준**이라 "점수가 더 좋아서 round7"은 아니에요. round7을 고른 진짜 이유는 **학습 데이터**:
    - round6 = **샘플링한 부분 데이터(8,028장)**, round7 = **전체 통합본(12,855장, 최신·내 Label Studio 라벨 포함)**.
    - 더 많고 다양한 데이터를 본 round7이 **test셋에 안 잡힌 실제 현장 상황에 더 견고할 것**이란 판단 + "최종 모델은 가진 데이터를 다 써서 학습한다"는 정석.
    - ⚠️ **순수 test 점수만 보면 round6도 정당한 선택**(특히 fallen은 round6이 더 높음). 그만큼 막상막하였고, round7은 "데이터 전체 사용" 원칙으로 고른 것.
  - (참고: round8 scratch 0.894와의 비교는 "전이+파인튜닝 > 맨땅"을 확인한 별개 실험.)
- **Q. 더 돌리면 더 좋아지지 않나요?**
  A. round9·10에서 해봤는데 **오히려 떨어졌어요(과튜닝)**. MLflow에서 하락 추세를 보고 멈췄습니다.
